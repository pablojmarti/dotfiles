description: Fix what a review or a bug file found. Run it in a new session.
argument-hint: "[review file or bug file]"
---
Fix what this file found: $@
If no file is named, use the newest file in docs/reviews/ or docs/bugs/.

Follow AGENTS.md, including "Done means". This fixes code that is already built; it is not a new feature. Do not commit.

1. Read the file, git status and git diff. For a review file, also read the feature's entry in docs/FEATURES.md and its walkthrough. If git status shows two or more other uncommitted files in docs/reviews/, this change has already been reviewed and fixed more than once: stop before step 2, tell me what the newest review still asks for, and ask me whether to go on. A third round usually means the reviews disagree with each other, not that the code is wrong. For a bug file, also read the code its Cause names, and run `sh scripts/check-bug.sh --again <the bug file>` (in the VM, where the play check runs): it reruns the Reproduce command. It builds first, so it never runs old code. Quote its "reproduced:" line. If it prints NOT REPRODUCED, the bug no longer shows: stop and tell me. If it exits 2, stop and tell me what it printed.
   Then list the files in docs/bugs/ and read the Cause line of each. If two or more other bug files name the same function, variable or buffer as this one, the same kind of bug may have come back: stop before step 2 and name those files. For each, say in one line whether its cause is the same kind as this one or a different kind. Then ask me: go on with the fix, or run /checkpoint? A third fix of the same kind in the same place usually means the design is wrong, not the line. If my /fix line already says to go on, or I have answered this question in this session, do not ask again.
2. List what you will fix. For a review file: every Must fix item, and every Should fix item in the same files. For a bug file: its Fix section, item by item, naming the same files and functions it names, and nothing else. For each, say in plain words what you will change. For a review file: if you think a finding is wrong, say why, with file:line, and do not fix it.
   For a bug file: if you think its cause or its Fix is wrong, list nothing. Say why, with file:line, and stop: I decide, and a wrong bug file is rewritten with /bugreport. Never list a different fix than the bug file gives, and never list a change to code the bug file says to leave alone. When the Fix says the test is wrong and the code is right, the fix changes the test; making the code match the test is a different fix. If the fixes need more than three code files, stop and tell me to run /checkpoint.

Then stop and wait for my OK. Change no files before it.

After my OK:
3. Fix only what the list names. If you cannot make a fix the way you listed it, stop and tell me why. Never switch to a different fix without my OK. If I write to you while you are working, stop what you are doing and do what the message says before anything else.
   For each test you add or change: write it first, run it against the code before your fix, and quote the failure line. A test that passes before the fix does not test the fix.
   Never change an existing test's assertion so that it matches what the code does now, unless the bug file's Fix names that test: then change what the Fix says, and keep every other assertion in the test. A changed test must check as much as before: fixed positions stay fixed positions, never a search for where the value is. If an existing test fails after your fix, or its name or comment says the opposite of what it asserts, stop and tell me: quote the test's name, its comment and the assertion, and ask which one is right.
   For a bug file, at least one test calls the same function the game loop calls, with no mock of our own code, and needs no display.
   If scripts/mutate-check.sh exists, run `sh scripts/mutate-check.sh` with no arguments after your fixes and quote its last line. Every line must be CAUGHT. If you cannot get there without changing more than the list names, stop and tell me why.
4. Run the full test suite, the Sanitize command from AGENTS.md and the app. Quote both summary lines. For a bug file, run `sh scripts/check-bug.sh --fixed <the bug file>` and quote its last two lines. The bug is fixed only when it exits 0. If it prints STILL FAILS, the fix did not work: stop and tell me. If it prints NEW FAIL, the fix broke something else: stop and tell me. If it exits 2, the check could not run, which is not a pass: stop and tell me what it printed.
5. Add a short "Fixed" section to the existing walkthrough of the feature that has the problem: what was wrong, the cause, and the test's name. Write the cause as one line in this form, both parts in backticks: `src/game.c:42` `if (score > best) {` (the line as it is now, after your fix). Do not write a new walkthrough.
   Then run `sh scripts/check-refs.sh <the walkthrough>`. Correct your "Fixed" section until the check reports no problem in it. If it reports a problem in an older part of the walkthrough, leave that part alone and tell me. Quote the last line. Rewrite docs/NEXT.md, 30 lines or fewer; do not add to it. Under "Where we stopped", say in one or two lines what the code does now. Do not tell the story of the fix, and do not name tests or functions that no longer exist. Do not tick, move or add features, and do not edit the review or bug file: never write "Fixed" into it; that belongs in the walkthrough. Then run `sh scripts/check-docs.sh` and quote its last line. It must say OK.
6. For a review file: list the findings you left, and ask me which to add under "Ideas" in docs/FEATURES.md.
7. End with what changed, the test summary, the check-refs last line from step 5, and for a bug file the check-bug last line from step 4. Then tell me to start a new session and run /review. Then stop. Do not commit.
